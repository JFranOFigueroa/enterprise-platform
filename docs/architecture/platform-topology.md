# Enterprise Platform - Topology

> Source of truth for namespace layout and ownership. Namespaces listed here are
> extracted from `platform/components/*.yaml`, `platform/storage/*.yaml`,
> `bootstrap/gitops/*` and `applications/<app>/app_vars/*.yml`.
>
> Note: there is **one** RKE2 cluster per environment deployment. The
> `apps-*` namespaces are environment partitions *inside* that cluster, not
> separate clusters. Multi-cluster is planned (ADR pending), not current.

## Ownership Boundary

| Layer | Owner | Mechanism |
|-------|-------|-----------|
| RKE2 install, OS, network, container runtime | Ansible | `rke2`, `common`, `ubuntu`, `containerd` roles |
| ArgoCD install | Ansible (once) | `gitops` role |
| AppProject, app-of-apps, cluster registration | Ansible (once) | `gitops` role |
| Namespace `gitops` Application CRs | Ansible (once) | documented exception, see below |
| `local-path-provisioner`, PriorityClasses, ClusterIssuers | **ArgoCD** | `ApplicationSet`, automated + selfHeal |
| Helm releases (platform components) | **ArgoCD** | `ApplicationSet`, automated + selfHeal |
| Application charts (`applications/*`) | **ArgoCD** | `Application`, automated + selfHeal |

Ansible bootstraps; it does not reconcile. Anything Ansible applies must not
also be managed by an ArgoCD `Application`, or the two will fight over the
resource and ArgoCD's `selfHeal` will revert Ansible's changes.

**Documented exception.** Ansible still creates the per-app `Application` CRs
(iumbit, atom, tenant-provisioning) because they inject per-environment secrets
from `applications/<app>/app_vars/` via `spec.source.helm.parameters`, and those
files are gitignored. Migrating them to SealedSecrets manifests is tracked as
follow-up work; until then these CRs are Ansible's and are not touched by
ArgoCD.

## Namespace Layout

### Application namespaces

| Namespace | Environment | Apps |
|-----------|-------------|------|
| `apps-dev` | `dev-local`, `dev` | iumbit |
| `apps-qa` | `qa` | iumbit |
| `apps-staging` | `staging` | iumbit |
| `apps-production` | `production` | iumbit, atom |
| `tenant-provisioning` | production (TPS itself) | tenant-provisioning |
| `tenant-<slug>` | per tenant, generated by TPS | iumbit (release `<slug>-iumbit`) |

`apps-production` also carries the namespace-level `ResourceQuota` and
`LimitRange` applied by `policies-app.yaml`.

### Platform namespaces

| Namespace | Contents | Owner |
|-----------|----------|-------|
| `gitops` | ArgoCD, app-of-apps, app-of-platform, all platform `Application`/`ApplicationSet` CRs, `tenants-repo-credentials` Secret | Ansible installs, ArgoCD self-manages |
| `cert-manager` | cert-manager controller + webhook | ArgoCD |
| `platform-monitoring` | kube-prometheus-stack (Prometheus, Grafana, Alertmanager, kube-state-metrics, node-exporter), PrometheusRules | ArgoCD |
| `platform-logging` | Loki, Promtail | ArgoCD |
| `platform-sealed-secrets` | SealedSecrets controller | ArgoCD |
| `kube-system` | metrics-server (RKE2-bundled CNI and core addons also live here) | ArgoCD / RKE2 |
| `local-path-storage` | local-path-provisioner | ArgoCD |

### Ingress

There is **no** `ingress-system` namespace. Ingress is provided by the RKE2
bundled `rke2-ingress-nginx` in `kube-system` with `hostPort` 80/443. The
obsolete `platform/ingress/nginx-values.yaml` was removed: deploying a second
NGINX Ingress controller would have fought the bundled one for the same ports
and produced duplicate, conflicting `IngressClass` objects.

## Cluster-scoped Resources

| Resource | Name | Owner |
|----------|------|-------|
| StorageClass | `local-path` (default) | ArgoCD (`platform-core.yaml`) |
| PriorityClass | `platform-critical`, `platform-high`, `app-low` | ArgoCD (`policies-app.yaml`) |
| ClusterIssuer | `selfsigned-issuer`, `letsencrypt-staging`, `letsencrypt-production` | ArgoCD (`platform-core.yaml`) |
| AppProject | `enterprise-platform` | Ansible (bootstrap) |
| LocalCluster | `cluster-<target_environment>` | Ansible (registration) |

## Bootstrap Order

`run-ansible.sh` → `site.yml` → `03-cluster.yml` (RKE2 ready) → `04-gitops.yml`:

1. Install ArgoCD in `gitops`, wait `Synced` + `Healthy`.
2. Apply AppProject, app-of-apps, cluster registration, app-of-platform.
3. Wait `app-of-platform` `Synced` + `Healthy`.
4. Wait for ArgoCD-owned `local-path` StorageClass **and** the provisioner pod
   `Ready` (PVCs cannot bind until the provisioner is running).
5. Wait for ArgoCD-owned PriorityClass `platform-high`.
6. Install cert-manager, wait for the `cert-manager` CRD to be `Established`,
   then wait for all three ClusterIssuers to exist.
7. Deploy applications, wire the TPS ArgoCD token, final gate.

Steps 4-6 are waits, not applies. They replace the `kubectl apply` calls that
previously made Ansible the second writer for those objects.

## Known Gap: app-of-apps Is Empty

`bootstrap/gitops/argocd/app-of-apps.yaml` watches
`bootstrap/gitops/applications/` with `directory.recurse: true`, but that
directory contains only a `.gitkeep`. It currently contributes nothing, and the
platform is actually reached through `app-of-platform` (which watches
`platform/components/`), which the `gitops` role applies directly.

Either populate `bootstrap/gitops/applications/` with the ArgoCD bootstrap
`Application` manifests, or drop `app-of-apps` and have the role apply
`app-of-platform` alone. Keeping an empty recursive generator in the path of
every sync is a trap for the next operator: a file dropped there would be picked
up by ArgoCD and applied without review or CI validation.

## Separation Principle

Platform services NEVER mix with business applications. The `platform-*`
namespace prefix and the `apps-*` prefix exist to make violations visible in a
namespace listing; the platform ApplicationSet is scoped to `platform-*` plus
`cert-manager`, `kube-system` and `gitops`, and application charts are scoped to
`apps-*`, `tenant-*`.
